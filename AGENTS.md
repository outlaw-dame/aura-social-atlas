# Runtime ownership and source-of-truth for all coding agents (read first)
- **Read [docs/ATLAS_RUNTIME_OWNERSHIP.md](docs/ATLAS_RUNTIME_OWNERSHIP.md) before deciding where Atlas's backend lives.** This repository is the source of truth for application code; Lovable is an **existing deployment and managed Supabase/Auth environment**, **not** the sole backend, not the GitHub substitute, and not a requirement for new code changes.
- Atlas's **social authority** is Fedizen/Bonfire. Atlas's **application server** is TanStack Start server functions and SSR in this repository, running in **Lovable Cloudflare Workers for the current preview** and **Railway Node/Nitro for isolated staging**. Atlas **application storage/session** uses two different Supabase projects by environment. The optional Fedify discovery gateway has separate Railway and PostgreSQL services. Do not conflate them.
- **Default task path:** inspect current `main`, PRs and CI → make changes through a narrowly scoped GitHub PR → test and review → deploy deliberately to the specified environment. Do not instruct Lovable agents to implement routine repo code or migrate databases by default. **Only** use Lovable for things genuinely hosted/configured there, including its current preview runtime, managed Supabase/Auth, and securely entered project secrets.
- **Railway deploys `main` (owner decision, 2026-11-22): Railway is the primary Atlas backend; Lovable is the legacy preview.** The `atlas-web-staging` Railway service builds `main` after its checks pass ("Wait for CI"); confirm the active deployment's commit before acceptance. Its Supabase project `nprmdytcoqiribpwedjc` is **not** the Lovable-backed users' database. Never transfer account/token data across environments by assumption. Staging diagnostics (`/fedizen-acceptance`) exist only where `ATLAS_FEDIZEN_ACCEPTANCE_PROBES=enabled`; elsewhere the page is not found.
- The tracked `.env`, Lovable-generated Supabase clients, `@lovable.dev/vite-tanstack-config`, and `LOVABLE_DB_MIGRATION_URL` reflect an **active legacy deployment**, not a requirement that every environment or new backend must use Lovable. Do not strip them without a tested replacement and explicit migration plan; do not follow them blindly when picking a database or build target.
- Domain: `atlas-social.space` is the purchased product domain, but full production migration and DNS delegation were **not completed at last review**. Current independent staging is `https://atlas-staging.damonoutlaw.xyz` behind Cloudflare Tunnel. Verify these statuses live before asserting changes.
- Always identify: **source branch + target runtime + target Supabase + OAuth/secret owner + precise acceptance gate**. Never print or copy private keys/tokens, enable native GraphQL reads without owner-v-anon testing, assume a server startup proves login/posting, or apply a migration to the wrong environment.

# Product scope and responsibility boundaries (highest priority)
- Atlas is a **Bonfire client**. Fedizen is the active Bonfire Community integration/test instance and future Fedizen flavor. Treat supported Bonfire APIs, Bonfire social identity, permissions and moderation as authoritative. Do not create a parallel social backend or assume the separate gateway replaces Bonfire.
- Use Fedify solely for optional, separately owned public ActivityPub relay discovery; `discovery-gateway/` is the active staging subscriber. Its actor, queue, indexes and Postgres are gateway-only. Never inject discovery into Bonfire Home, reuse Fedizen signing credentials, modify Fedizen DB, bypass Bonfire moderation or claim gateway results are the user's follow timeline.
- `relay/` is an optional relay-server experiment and `bonfire_relay_client/` is an inactive host-dependent adapter; don't duplicate these into the gateway or install the adapter on Fedizen without explicit operator and host-version approval.
- Treat sample creators/stories, local follow/save choices and composer drafts as prototypes until backed by real Bonfire account APIs. Never represent local selections as synced follows, bookmarks or published posts. Prioritize real OIDC/account session and authorized Bonfire feed/actions before new relay or infrastructure features.
- Before introducing a service, persistence layer, authentication mechanism, protocol adapter or Bonfire patch, justify which layer owns the behavior, the actual supported API, security boundary, user benefit, and integration test. Prefer the minimum client-side integration and keep gateway failures independent of Bonfire login, feed and posting.
- Distinguish code/test existence from live verification. A passing synthetic relay or gateway deployment does not establish Fedizen client sign-in, API compatibility or native Bonfire write capability.

# Architecture
- Initialize account state through the subscribe-first session observer and associate loaded profiles with their user ID; delayed reads must not overwrite newer auth events or display another account's profile.
- Share article creator attribution through CreatorTag across phone and desktop feeds; profile and follow actions use the existing discovery state so author interactions stay consistent.
- Open-web article authors (Spotlight, readers): resolve in src/lib/article-author(.server).ts — the article's ActivityPub attributedTo first, then fediverse:creator via WebFinger, else the plain byline. Credit an actor only if it shares the article's host or lists that domain in attributionDomains; fetch only through safeFetch (public https, every hop resolved over DoH and refused unless all addresses are public, re-validated redirects, timeout, size cap); always re-fetch attributedTo actors from their own server, never trust embedded copies and never block Spotlight past its time budget.
- Fedizen feed and Saved posts carry `article` (Bonfire's link preview, else the first ordinary link; never mentions, hashtags or collection links) and get "More from" through the same resolver (withArticleAuthors, 2 s budget, shared cache). Render with AuthorCards / PostArticleCard (desktop) and f7 ArticleCard (phone); verification labels live in ATTRIBUTION_NOTE. Bonfire's preview author_name is shown only as a plain, unlinked byline.
- Author discovery order: attributedTo → fediverse:creator → author links (rel="author" in the page, or a link preview's author_url passed as a hint) fetched as ActivityPub actors ("author-link"). Every path uses the same trust rule (actorMayClaim). Podcasts (Castopod): a PodcastEpisode credits its attributedTo podcast (work "episode"); a link that is an actor's own page credits that actor (work "podcast" when application/podcast-activity+json returns the same id typed Podcast, else "account"). Use CREDIT_LABEL / attributionNote for labels; feeds drop a credit equal to the post's author (creditsBesidesAuthor). Episodes play in place: the resolver captures a PodcastEpisode (only with a verified podcast) and episodeFor(url) attaches it to post.article.episode; EpisodePlayer (desktop) / f7 EpisodePlayer (phone) render it in place of the link card, and all share one audio element via src/lib/podcast-player.ts (one episode at a time, Media Session, back 15 s / forward 30 s). Keep post actions below the player. The mini player (MiniPlayer, desktop in Discovery, phone in AtlasMobileApp above the tab bar) shows whatever is loaded and sets --atlas-player-offset, which floating buttons (Compose) add to their bottom margin. Colors come from the reader's accent (src/lib/accent.ts, Settings → Appearance): use var(--accent)/bg-accent, never a fixed red. Podcast profile cards say Subscribe (followLabels). Video: FediVideo (src/lib/fedi-video.ts) comes from PeerTube Video objects (resolver captures it like episodes; mediaFor(url)), Bonfire video attachments (videoFromAttachment) and video podcast enclosures; render with VideoPlayer, never a bare <video>. One shared element (src/lib/video-player.ts) moves between the post and the floating VideoDock (Arc-style; desktop via DesktopHosts, phone in AtlasMobileApp) — move it with appendChild in the same task, never recreate it. HLS uses hls.js, lazily. PeerTube embeds only as the fallback, only /videos/embed/ on the video's own host, sandboxed. Channel outboxes reference videos by URL; loadFediProfile fetches them (same host). Audio and video pause each other (media-focus.ts). Voices to know: voices.server.ts (FediDB popular accounts + server software, Castopod Index), curated lists in voices.ts.
- Author tags never leave Atlas: call openFediProfile({ actor, acct, name }) (src/lib/fedi-profile.ts); FediProfileDialog (desktop, mounted in Discovery) and f7 FediProfilePopup (phone, mounted in AtlasMobileApp) listen. Profiles load through loadFediProfile (actor from its own server, handle confirmed by WebFinger, followers/outbox only from the actor's host, public Create posts by that actor only, one 4 s budget for the whole load, cached). Follow only a WebFinger-confirmed handle (checked again server-side against the actor) through Fedizen: accounts/lookup (Bonfire fetches remote accounts via WebFinger) then accounts/:id/follow.
- Feeds has five kinds (src/lib/feed-types.ts; desktop FeedsView, phone MobileFeeds): Following (/api/v1/timelines/home), For You, Articles, Local (Bonfire's local timeline) and pinned Circles (/api/v1/timelines/list/:id — Bonfire serves circles through the Lists API). For You (getForYou) merges the home timeline, timelines for the first 4 followed hashtags (/api/v1/followed_tags) and the most-replied posts of the last 7 days in groups the person has joined (GraphQL feed sortBy REPLY_COUNT, timeLimit 7, like Bonfire's trending_discussions preset; membership: joinedGroups walks every directory page, cached 10 min, and checks relationships 40 ids at a time, cached 5 min per person and cleared on join/leave; an incomplete walk reports "groups" as missing), then rankForYou: one entry per post with every reason shown as chips ("Popular in" carries the joined group's id and avatar, matched by name: the chip shows the group's avatar before the name, and the name opens the group — phone via openGroup()/OPEN_GROUP_EVENT into GroupPopup, desktop /groups?group=<id>), recency half-life 12 h. Pinned circles are kept per Atlas user in localStorage (atlas-pinned-circles:<uid>, max 12) — this device only until a Supabase column backs them; deleting a circle unpins it. New Fedizen routes must be added to the READS allowlist with a schema.
- Feeds tabs follow Particle (useFeedTabs in useFeeds.ts; phone MobileFeeds, desktop FeedsView): plain names, the open one in a filled pill, and an accent dot before any feed with a post newer than the newest the person last saw there (atlas-feed-seen:<uid> in localStorage, never moves backwards; a feed seen for the first time takes its newest post as the baseline; the open feed counts as seen as it updates, but only while it is on screen — never under another dock tab or in a background browser tab; views pass null until they've restored the last open feed). The dots reuse each view's own queries; Following's dot follows whichever source the view shows (desktop: Bonfire native home when verified). Disconnecting Fedizen clears For You and circle caches too; joining or leaving a group refreshes For You, and circle membership changes refresh pinned circle feeds.
- Feed post cards (phone MobilePostCard + PostActions, desktop FeedPostCard) show avatar (initial when missing), name, handle and a short time that opens the post, then the standard actions: Reply, Boost, Like, Save, Share with counts. Reply/Boost/Like/Save write to Fedizen as the person (POST /api/v1/statuses/:id/favourite|unfavourite|reblog|unreblog|bookmark|unbookmark; replies POST /api/v1/statuses with only status, in_reply_to_id and visibility — the post's own audience, unlisted when unknown; Bonfire rc.1 masto_compatible_router). Private and direct posts can't be boosted. Like and boost state is shared across views (useReactions), one write per post and kind at a time. A post with no status id offers Share only; group posts carry their Bonfire object id as status id and For You reads each one (GET /api/v1/statuses/:id) for the person's like, boost and bookmark state and counts, keeping Share only when that read fails. Block and unblock refresh every personal feed, For You and circles included. Share uses the system share sheet, else copies the link.
- Phone navigation: a feed-like destination (a hashtag's feed) is pushed, never a sheet with a close button. pushPage() in src/components/f7/navigation.ts navigates the .atlas-stack view laid over the tabs (z 500, under the tab bar at 600), whose root is an empty transparent page: back chevron, left-edge swipe back on both themes, the tab bar stays, and tapping a tab pops to the root. It's a separate view because Framework7 9 keeps one page behind the current one and rebuilds older ones from routes, and the main view's root (all the tabs) is inline with no route. While pushed, the side panel's edge swipe is off. Sheets stay for tasks and quick looks (compose, messages). Settings mirrors desktop's /settings: the same categories in the same order (Intelligence, Notifications, Appearance, Moderation, Followed hashtags; f7/SettingsPages.tsx), each a pushed leaf page, and each keyword filter has its own page (/keyword-filters/:id/) with everything desktop's editor has.
- Push notifications go through Atlas's relay (src/lib/push/relay.server.ts; Settings → Notifications on both platforms), never straight from Fedizen to a browser: Bonfire puts the account's access token in every Mastodon-shaped push payload (MastoPushAdapter.payload). Fedizen subscribes to /api/push/relay/<relay_id> (one relay per person; its P-256 key sealed with a key derived from ATLAS_VAPID_PRIVATE_KEY; Fedizen's server_key kept to check its VAPID signature); Atlas decrypts (RFC 8291, src/lib/push/webpush.ts, Web Crypto only, tested against the RFC's own example), keeps only title, body and kind, and pushes to each of the person's browsers with its own VAPID key (ATLAS_VAPID_PUBLIC_KEY / ATLAS_VAPID_PRIVATE_KEY / ATLAS_VAPID_SUBJECT secrets; scripts/vapid-keys.ts), only to known push services. The /app service worker shows them and a tap opens Activity. Alerts and policy (everyone / people you follow / people who follow you) are Mastodon's, applied by Fedizen. Tables atlas_push_relays and atlas_push_devices (supabase/migrations/20261117020000_push_relay.sql) are server-only.
- Live updates (GET /api/live → src/lib/live.server.ts; LiveUpdates mounted in DesktopHosts and AtlasMobileApp) replace polling while a page is visible: the server opens Fedizen's Mastodon WebSocket stream (`user`; token in Sec-WebSocket-Protocol, since Bonfire's Authorization lookup only reads x- headers) or, failing that, Bonfire's SSE stream (notifications, messages, unread count), and sends the browser only Atlas's own events (live-events.ts; posts re-checked with the timeline schema; never the token or Bonfire's notification text/links). New Home posts go through useHomeTimeline's pill; deletes hide the post (markDeleted); notifications refresh Activity. Streams end after 25 min and reconnect with backoff; Home's own checks drop to every 5 min while posts arrive live.
- Activity (desktop ActivityPage, phone MobileActivity) is grouped as Mastodon 4.3 and Bluesky show notifications: likes, boosts and follows on the same post in one row with the faces of who did it ("Ann, Ben and 3 others liked your post"), and All / Mentions (Bluesky's tabs). It reads Fedizen's /api/v2/notifications (Bonfire groups within each page: SocialMastoAdapter.grouped_notifications), joins groups split across pages (mergeNoticeGroups), and loads older pages on request; a Fedizen that can't answer v2 gets single notifications.
- Following hashtags works as in Mastodon, never Bonfire's own route: Follow / Following on the tag's page (phone navbar right, desktop header) and Settings → Followed hashtags (phone pushed page /followed-tags/, desktop /settings/hashtags) with Unfollow per row. Writes: POST /api/v1/tags/:name/follow|unfollow (bonfire_tag MastoTagController; following creates the tag; unfollowing an unknown tag answers 404, treated as not followed). The list reads followed_tags?limit=200, Bonfire's maximum page. useTagFollow updates ['fedizen-followed-tags', uid] at once, reverts on failure, and refreshes For You.
- Compression: the discovery gateway compresses its public /api/ JSON itself (discovery-gateway/src/compress.ts: zstd 6 → br 5 → gzip 6 by Accept-Encoding q-values, ≥1 KB, Vary: accept-encoding, never on the admin listener, zstd window within RFC 9659's 8 MB). The Atlas web app runs on Cloudflare Workers, where Cloudflare compresses responses to visitors; don't hand-compress there. Never compress a response that mixes a secret with attacker-influenced content (compression side channels).
- Bundled images: avatar presets ship as 512 px AVIF (≤ ~16 KB) with WebP copies, encoded by scripts/encode-avatars.py at the lowest quality keeping SSIM ≥ 0.985 against the resized PNG master; the ~1 MB PNG masters stay in src/assets/avatars as sources and must not be imported. A capture-phase error listener in atlas-avatars.ts swaps a preset's AVIF for its WebP if a browser can't decode it. The sample news photos ship as AVIF where scripts/encode-photos.py finds a quality keeping SSIM ≥ 0.985 against the JPEG with ≥ 20 % saving (architecture, design, travel: 205 KB → 96 KB); the star field stays JPEG. Their JPEGs are the registered fallbacks. All bundled AVIF fallbacks go through src/lib/image-fallback.ts. GIFs from Mastodon arrive transcoded to video (attachment type gifv) and play as GIFs (VideoPlayer → GifVideo: inline, muted, looping, no controls, GIF label, only on screen, paused under Reduce Motion until tapped), never with the video player or mini player. PWA icons stay PNG (manifest and apple-touch-icon).
- Don't tell people what they already know. No "You follow" chips (only "Popular in [group]" explains a For You post), no "Hashtag" label or "You follow this hashtag" note on a tag's feed (its title is the tag), no captions restating a navbar. Keep a line only when it adds something the reader can't see, such as a source ("From mastodon.social") or an error with its fix.
- Color theme (src/lib/theme-mode.ts, Settings → Appearance on both): Light, Dim, Dark, Match device; Match device picks Dim, not Dark, on a dark device. Kept in localStorage (atlas-theme); ?mode=light|dim|dark|auto overrides it for one visit. Dim is `class="dark"` plus `data-theme="dim"` on <html>, so every dark style applies and only the palette changes: shadcn tokens and Framework7 variables under [data-theme="dim"] at the end of styles.css (charcoal #191C22 page, #242830 cards, #30353F raised; text #F3F1ED / #B3B4BA, AA on all three). New dark colours need a Dim value too; write greys as hex or srgb (oklch mixes turn them brown). THEME_BOOT_SCRIPT in __root.tsx applies the theme before first paint; anything that sets the theme after hydration reads currentAppearance(), never the hydration render's 'light'. Framework7 gets no darkMode prop: it starts from <html>'s class and follows f7.setDarkMode.
- Posted hashtags read as the word alone, as Threads shows topics: people type the # in the composer and text fields, but wherever a tag is shown as a link (post text, bios, profile and story tags, collection tags, tag page titles) render it with TagText — the # stays in the text, visually hidden (.atlas-hashtag-mark), so copying keeps it — and label the control with hashtagLabel(tag). Editors and plain-text metadata keep the #. Hashtags in post text are links in the accent colour (linkifyHashtagsWith): on the phone they open TagFeedPopup (openTag()/OPEN_TAG_EVENT), on desktop /tags/$tag. Both read Fedizen's tag timeline through the person's connection (getFedizenTagFeed, /api/v1/timelines/tag/:tag?limit=20), so they hold only posts the person may see and act on; only signed out or not connected do /tags/$tag and the phone's TagFeedPage (PublicTagPosts) fall back to the public mastodon.social feed (getTagFeed) — a connected person whose Fedizen read fails or whose access lapsed sees that problem with retry or reconnect, never another server's posts. Pages outside Discovery that render posts must mount DesktopHosts (FediProfileDialog via useFediProfileOpener, CollectionDialog via useCollectionOpener, MiniPlayer, VideoDock) — Discovery passes its own collection opener, /tags/$tag uses StandaloneDesktopHosts. Anything a post dispatches as a window event needs its listener there. Followed hashtags (getFollowedTags, /api/v1/followed_tags?limit=100) a post uses — or For You found it by — show at its top left as a tag icon and the tag, in the text colour not the accent, after Ivory (FollowedTagLine); each opens its feed, and a tag's own feed doesn't repeat it. This replaces For You's hashtag chip.
- Mentions in replies follow iMessage (MentionField, shared by the phone reply sheet and desktop reply dialog; helpers in src/lib/mentions.ts): typing "@" and the start of a name shows a strip of people under the box (the author being replied to first, then Fedizen's GET /api/v1/accounts/search?q=…&limit=6, debounced, at most three) with picture and name, plus the typed text to keep it as is. Picking one inserts their handle (short for fedizen.net people, full otherwise) and tints it in the accent; only picked mentions are tinted. The tint is a copy of the text behind a transparent-text textarea, so both must share every layout metric. Arrow keys, Enter/Tab and Escape work on desktop.
- Link previews use RichLink (both platforms): Bonfire's card image runs edge to edge and fades into a panel tinted by a blurred copy of itself, with favicon, publisher, headline and summary, after Particle's story cards. Without an image it's a plain panel. Creator attribution lives inside the same card, under a hairline: each verified creator ("More from", avatar in the reader's avatar shape, name, handle, chevron) opens their profile in Atlas, followed by how Atlas verified them; with no verified creator, the publisher byline goes on the card's host line. The separate AuthorCards / f7 author rows are used only when a credit has no preview card. Episodes and videos still play in place instead.
- New posts waiting above Home show as a pill with an arrow and up to three overlapping faces (NewPostFaces; lib/new-post-faces.ts), after Ivory and Mastodon for iOS, on desktop and phone: different people, newest first, a boost's booster rather than its author, and only from posts the reader's filters would show (useShownPosts). The visible count is gone; the button's label says it ("Show 5 new posts from Ann, Ben and others").
- On tab-bar phones (html[data-nav="tabbar"]) other card footers put the actions on the left and the date on the right, and each tab ends with extra scroll room, so the floating Compose button never covers the actions. Keep Compose floating.
- App dock order is Feeds, Discover, Groups, Activity, then the person's avatar (Profile); the tab bar, side tab bar, rail and sidebar all render the same `dock` list. Settings is reached from Profile and the sidebar, Saved is a tab on Profile.
- The desktop page (`Discovery.tsx`) uses the same order in its sidebar: Feeds (`/feeds`), Discover (`/`), Groups (`/groups`), Activity (`/activity`), Profile (`/profile`, desktop `ProfilePage`), then Settings. `/following` redirects to `/feeds` and `/saved` to `/profile?tab=saved`; keep those redirects for old links.
- Profile is the dock's last tab (ProfileView), structured like a Bluesky profile: banner, avatar, Edit profile, name, handle, counts, bio, then tabs Activity (posts, quote posts, replies and boosts in one tab; replies and boosts toggle, after Mastodon's 2026 profile redesign), Featured (Mastodon 4.4: featured hashtags and featured profiles), Media, Collections (Mastodon 4.6; phone and desktop), Saved (your Fedizen bookmarks; not locked: each saved post keeps the audience its author gave it), Liked (GET /api/v1/favourites; only you see it, as on Mastodon and Bluesky), Circles (your Bonfire circles via Mastodon's Lists API: list, create, rename, delete, add/remove people). No Lists tab: Bonfire serves lists from circles, so it would repeat Circles. Old ?tab=posts/replies/feeds/lists links open Activity/Circles. Settings → Moderation (desktop /settings/moderation, phone pushed page /moderation/, same order) has separate lists: keyword filters are Atlas's own (see Intelligence below), blocked instances open Fedizen's page (no client API in Bonfire v1.1.0-rc.1), blocked people are listed and changed in Atlas (/api/v1/blocks, accounts/:id/block|unblock), and so are muted people (/api/v1/mutes, accounts/:id/mute|unmute). Post More menus (desktop PostMoreMenu, phone MobilePostActions) and profiles (FediProfileDialog's More, f7 FediProfile's navbar More) offer Mute / Unmute and Report for someone else; Report follows Mastodon's steps (category spam|violation|legal|other, a note ≤ 1000, forward to the account's own server only when it's elsewhere) through POST /api/v1/reports. "Liked by…" / "Boosted by…" read statuses/:id/favourited_by|reblogged_by. Composers (desktop PostComposer, phone ComposeSheet, MentionField replies) suggest hashtags after "#" (HashtagSuggestions: the tags you used in your 40 newest posts first — accounts/:id/statuses?exclude_reblogs=true — then /api/v2/search?type=hashtags; right after "#" alone, your recent ones; Bonfire's GraphQL tagSuggestions returns accounts, not tags), and the composers suggest people after "@" with picture and name (MentionSuggestions, the same search as replies). Bonfire lists every silenced account as muted and a block silences too, so the Muted list leaves out people you block; people and instances stay in separate lists. Post search with Intelligence on also runs up to four wordings from the person's own model (searchWordings) and says which it added. Search by meaning (src/lib/semantic, useSemanticIndex; Settings → Intelligence, opt-in per device) is Atlas's web emulation of ObjectBox's on-device vector index: posts shown in feed cards (FeedPostCard, MobilePostCard; never direct messages) are embedded and kept in IndexedDB per Atlas user and model (≤ 4000, oldest out; cleared on sign-out or from Settings), and post search adds "Related posts you've seen" (cosine ≥ 0.35, full scan). Engines: EmbeddingGemma 300M on the device (embed.worker.ts: Transformers.js 4.3.2 from jsDelivr, run only if its SHA-384 matches the npm file; model onnx-community/embeddinggemma-300m-ONNX q4, ~197 MB once, WebGPU else WASM; query/document prompts from the model card; vectors cut to 256 and re-normalized), or the Intelligence key's provider (embeddings.ts: OpenAI text-embedding-3-small at 256, Gemini gemini-embedding-2 cut to 256, Mistral mistral-embed at 1024, Cloudflare @cf/google/embeddinggemma-300m sharing the on-device index; Anthropic and Kimi have none). Vectors are only compared within one model's index. Keyword filters checked in context use it too (FilterEngine `similar`, makeSimilar): each such filter's words and wordings are embedded once as a search, posts reuse their indexed vector; cosine ≥ 0.40 sends the post to the AI model to confirm (visible meanwhile), and with no AI model only ≥ 0.55 filters, noted as "close in meaning". Never direct messages. Follows open from the Following count, never as a tab. Never seed fictional personal content for its empty sections (Groups follows the same rule).
- Collections follow Mastodon 4.6 (src/lib/collections*.ts): name ≤ 40, description ≤ 100, one topic hashtag, ≤ 25 accounts, ≤ 10 per person, public or unlisted, sensitive flag. Only add an account when its own server's `feature_approval` allows `public`; unknown or missing means no. Atlas collections live in server-only tables (drizzle/migrations/0003_collections.sql) written only through collections.functions.ts; Mastodon collections are read through safeFetch.

- Fedizen content: read public Bonfire data via its GraphQL API (feedName "articles" for Recent Articles, "local" for the signed-out public feed; fall back to object.creator when subject is hidden) in src/lib/bonfire.server.ts; never inject remote HTML. Posts keep plain-text paragraphs (htmlToParagraphs) for filters, search and previews; their formatting is read into the closed model in src/lib/rich-text.ts (allowlisted elements, http(s) links only, bounded size and depth) and drawn by React in PostBody.tsx. Misskey's MFM: FEP-c16b `mfm-*` spans (as Bonfire's MFM parser writes them) and, for Misskey-family posts read from their own server, the MFM source via mfm-js (src/lib/mfm.ts, server only). MFM arguments are validated and clamped before reaching a style, effects are clipped to their paragraph, animations stop under Reduce Motion, and clickable/followmouse stay inert. Mastodon REST timelines on Fedizen require login.
- Collections (Mastodon 4.6, FEP-7aa9): Bonfire v1.1.0-rc.1 has no collections support (no /api/v1/collections, no FeaturedCollection/FeatureRequest), so Atlas reads Mastodon collections from their own servers and keeps Atlas-made ones in server-only tables, labelled as not federated. Featuring requires the account's own `feature_approval` to allow it. When Bonfire ships FEP-7aa9, move Atlas-made collections to Fedizen rather than federating from Atlas.
- Opening a post: clicking or tapping a post card (anything but a link, control, media or text selection; src/lib/open-post.ts) or its time opens its conversation in Atlas — /post/$id on desktop (ThreadView.tsx), a pushed /post/:id/ page on the phone (f7/Thread.tsx) — never Fedizen's page, which stays in the post's More menu ("Open on <host>"). The conversation is Fedizen's /api/v1/statuses/:id/context (Bonfire's own reply tree; it doesn't fetch missing remote replies), arranged by src/lib/thread.ts: ancestors oldest first with a gap note when the parent is missing, the author's own follow-ups straight after the post, replies nested, sorted Oldest/Newest/Top with the author's and the reader's replies first, 40 top-level replies per page; how replies fold and how deep they nest is Atlas's folding rule (src/lib/folding.ts).
- Translation (src/lib/translation/*, useTranslation.tsx, TranslationSettings.tsx + f7/TranslationSettings.tsx under Settings → Intelligence; tests/translation.test.ts), after Phanpy's (status.jsx, translation-block.jsx) and improved. A post's language is Mastodon's `language` (kept in FedizenPost), else detected on the device once on screen (browser LanguageDetector, else tinyld light then normal; under 50% is no guess). Offered for languages the person doesn't read (settings: target, languages read, both defaulting to the browser's); translated in place with "Translated from X · via · Show original" and a source picker, in PostContent and MobilePostContent (feeds and conversations). Automatic translation as posts come into view is on, but on this device only unless the person allows the service too. Engines in order: on-device (browser Translator API, desktop Chrome/Edge; a language download only during a tap; one at a time), then the chosen service — DeepL with the person's key (server only: DeepL refuses browsers; key in the vault as provider 'deepl', supabase/migrations/20261118000000_translation_keys.sql; tag_handling html; Free keys end ':fx' → api-free.deepl.com) or their Intelligence AI provider (tasks.translateTexts, tags kept). Only public/unlisted posts ever leave the device. What's translated: CW, every paragraph (in quotes, lists, centre), poll option titles; mentions, hashtags, links' addresses, emoji, code, times and MFM are kept exactly (segments.ts: `html` form with translate="no" spans for DeepL/AI, `plain` form with {n} placeholders for the browser, which drops inline formatting; nothing an engine returns can add markup). Settings are on the device (atlas-translation), the DeepL key with the account. Fedizen: Bonfire 1.1.0-rc.1 includes bonfire_translation (LibreTranslate and DeepL adapters, instance-configured) but exposes it only to its own LiveView pages — not the Mastodon API (no /api/v1/statuses/:id/translate) nor GraphQL — so Atlas can't use instance translation yet.
- Open conversations stay current (src/lib/thread-live.ts, useThread.ts; tests/thread-live.test.ts). Fedizen's API has no per-conversation stream (Bonfire's own pages get :new_reply via LivePush, not exposed), so useThread reads the context again on a live post that is or answers one of its posts, on any live notification (both settled 800 ms), every 45 s while visible (react-query refetchInterval; paused when hidden), on focus and on reconnect. Reads are reconciled with what's on screen, never replacing it: edits show in place; a post deleted (live delete event or the reader's delete: deletedPosts) or missing from a complete read becomes a tombstone placeholder (`tombstone: true`, nothing it said kept) so replies keep their place — a partial read never tombstones; new replies are added at once, in place, never behind a button: useScrollAnchor keeps the post being read (the one across the line 40% down the screen) where it was, adjusting the scroll itself rather than relying on the browser's scroll anchoring. Posts new to the reader (arrived while open, or newer than their last visit; never their own) carry a "New" badge in their branch colour, and arrivals glow briefly (none with reduced motion); a screen-reader status says what arrived. Folding decides each set once per visit after calibrating, so arrivals and new measurements never fold or unfold under the reader. The visit's read mark follows what's shown.
- Conversations have one design (decided Nov 2026 after comparing two prototypes; the other, a Wavelength-style chat with a Conversations list, was removed): ConversationThread.tsx, shared by desktop (ThreadView.tsx) and phone (f7/Thread.tsx) with the platform's FilterGate/MobileFilterGate and PostContent/MobilePostContent so no layout skips filters, warnings, the media veil or any content; parts in ConversationParts.tsx; model in src/lib/conversation.ts. No prototype labels or names in the UI (never "Atlas folds" either). Drawn as Phanpy's contextual timeline: one column, avatars joined by a 3px line above the opened post (the "hero": larger, faint band, full date and counts, actions always shown), "Thread n/m" badges for the author's self-thread, replies curving off a grey trunk and indented per level, Phanpy's kind colours (orange reply-to/Thread, purple boost), plus Bonfire's Nested/Flat (atlas.proto.replyMode), sorting and participants. Folding (src/lib/folding.ts, tests/folding.test.ts; the rule combines what Phanpy and Bonfire do, both described there with sources): a set folds when everything under it would take more than 3/4 of the window (estimated pixels at this width: text lines, media at its drawn size up to 320px, polls, cards; corrected once per conversation and width, before paint, by the median drawn ÷ estimated height of the replies on screen, held to 0.6–2), a conversation fitting in 1.5 windows is all open, and a set holding the author's, the reader's, a followed person's, a mentioning or a new-since-last-visit post never folds by itself (followed via useFollowedAmong, the batched relationship lookup); − / + (44pt target) on every set, the line itself taps to fold, Collapse replies / Expand all, summaries with faces, "N replies · M in total · latest", reasons and a filter-gated preview of the first reply, »; folded replies stay in the page as hidden="until-found" so find-in-page opens them; the reader's folds are kept per conversation in localStorage (atlas.proto.folds, 100 conversations; once they've folded anything the bar says "Your folds are kept on this device only" — never present them as synced); a visit is one per conversation page (useConversationVisit): where the reader left off is read once and recorded once Fedizen answers (atlas.proto.conversations, on this device: Bonfire's per-thread Seen isn't in its API; never present it as synced); indentation stops at 3 levels on narrow screens and 5 on wide, deeper replies say "Replying to". Lines are coloured per branch (branchesOf; --atlas-branch-0…5, light and dark), Atlas's addition: Phanpy's own lines are grey. The atlas.proto.* storage keys predate the single design and are kept so readers' choices carry over.
- Native Bonfire Home (ATLAS_BONFIRE_NATIVE_GRAPHQL_READS=verified; desktop Following only): GraphQL `me.myFeed` decides the page, order and cursor; hydrateNativeBonfireHome (bonfire-private.server.ts) reads each post's REST status (the GraphQL post id is the status id; 8 at a time, 2.5 s budget, reads past it never sent) so cards match the REST feed, keeps a boost's booster from GraphQL, and leaves a post it couldn't read as the GraphQL-only card (Share only). Then the same enrichment as every feed (feed-enrich.server.ts: More from, avatars, reply parents). A card not read in time carries `statusRef`; useFedizen asks getNativeHomeDetails for those right after (8 s, up to 20) and swaps them in place (withNativeDetails), so the first page never waits on slow posts (bridged Bluesky posts are the usual ones). New posts: useNativeNewPosts checks getNativeBonfireHomeLatest (the newest GraphQL page as GraphQL-only cards, no per-post reads) on useHomeTimeline's rhythm; the same faces pill shows them, and tapping it reads native Home again from the top. Activity stays the REST notifications Home already read.
- Editing your profile with Fedizen connected edits your Fedizen profile (fedizen-profile*.ts, useMyFedizenProfile; desktop EditProfileDialog, phone EditProfileSheet): name, bio, website and location through Bonfire's GraphQL `me` and `updateUser(profile:)`, only after verifiedNativeBonfireConnection matches the linked account, writes only with a `write` grant. Limits are Bonfire's (name 1–100 required, bio ≤ 10,240). Bonfire links a saved bio's addresses, mentions and hashtags, so Atlas edits it as text (bioAsText) and never sends links back. Featured hashtags stay Atlas's (Fedizen has none); Atlas's own bio is for accounts without Fedizen. Avatar and banner uploads (`images`) aren't sent yet.
- GraphQL or REST: Fedizen serves both over the same Bonfire data. Use whichever does more on Fedizen's version: GraphQL for Bonfire's own concepts (groups, boundaries, quotes, profile fields and images, native Home), REST where GraphQL is missing or weaker (undo boost, changing mutes and blocks, polls, messages, followed hashtags, push). Don't move a working REST path to GraphQL unless it gains the person something; record the reason in docs/BONFIRE_GRAPHQL_CAPABILITY_MATRIX.md (its "Which API" section and roadmap).
- Fedizen rate limits (src/lib/fedizen-rate-limit.ts; every REST read, write, upload and GraphQL request goes through it): after a 429 an account's requests wait out Retry-After (1 s–2 min, 15 s default) without being sent; GraphQL never retries a 429; when 3+ accounts are limited within a minute, every account waits (Atlas reaches Fedizen from one address). Single-post reads (GET /api/v1/statuses/:id) are reused for 30 s per account and dropped whenever that account writes, so its own actions always show. Accounts are keyed by a SHA-256 of the token, never the token. Don't add retries on 429 anywhere.
- Fedizen API access: a separate "Connect Fedizen" OAuth asking for `read write follow` (FEDIZEN_API_SCOPE), so Atlas can read the timeline and notifications and act for the person (join/leave groups, follow, post). Atlas is not read-only. Connections made under the old `read` scope keep reading but must reconnect once before any write (`hasScope`); the registered OAuth app records its scopes and is re-registered when they change. PKCE, per-callback app registered via /api/v1/apps; stored in server-only tables (no anon/authenticated grants); tokens never leave server functions in src/lib/fedizen.server.ts. Private reads (`fedizenGet`) and writes (`fedizenSend`: group join/leave, follow/unfollow, bookmark/unbookmark, and circles via /api/v1/lists, each with its method and only body) go through explicit path allowlists with a zod schema per endpoint, bounded bodies, `redirect: 'error'` and `no-store`; add an endpoint only with its schema and a test. Every personal server function binds `expectedAtlasUserId` to the verified session. Bonfire rc.1 ignores `limit` on some lists (follow requests: Requests.list_requesters, paginate false), so their schemas must not cap the length below what Bonfire can send; keep the first page in the server function and report the total. Failed private reads log their route (readRoute: ids, handles, tags and queries become :x) and status or mismatch paths, never values. Migrations outside the journal (drizzle/migrations 0003_collections, 0004_fedizen_app_scopes, 0005_fedizen_connection_client) are applied by hand; until 0004 is applied, connecting reuses the existing OAuth app, and until 0005 is, Disconnect revokes by trying every registration. Disconnect revokes the grant at Fedizen (RFC 7009) before deleting it.
- Optional relay: relay/ is a standalone Bun + @fedify/relay package outside the app build (one process per protocol, own origin and PostgreSQL); Atlas is a Fedizen client, so the relay never auto-deploys or auto-subscribes and only an instance admin subscribes. Keep it allowlist-only, relay only public content from currently subscribed servers (authoritative check runs after Fedify signature verification; Follow/Undo/Accept/Reject are a separate control plane), forward signed bodies byte-for-byte, keep /healthz free of configuration details, pin @fedify/* exactly (it hooks an internal method), and keep relay tests offline via its fetch-blocking preload.
- Bonfire relay client: bonfire_relay_client/ is a standalone Elixir extension outside the app build. It keeps a dependency-free pure core so it can be tested offline. All signing, delivery and fetching go through the Federation behaviour; the Bonfire adapter is capability-gated on the hooks in upstream_patches/ and fails closed without them. Relay subscriptions use the instance service actor only, never a user's follow graph. Hashtag and instance rules are local filters on delivered content, kept separate from selective sources like FediBuzz. Every admin call re-checks authorisation on the server, and the feature stays off by default with connections created idle.
- Relay-client host integration uses a source-matched custom Community image and a full digest override selected from the host's exact Co-op Cloud recipe image expression/overlays; variable names differ across revisions, displayed versions/recipe labels are not provenance, and patch fit does not establish full host compatibility.
- Fedizen runs Bonfire Community **v1.1.0-rc.1** (`BONFIRE_VERSION` in src/lib/groups.ts). Groups come from its public GraphQL API, read without sign-in so Bonfire applies each group's boundaries (hidden groups and members-only posts never come back): `categories` / `category(categoryId)` with `boundaries{key slug}` for membership, visibility and participation, and `feedActivities` with `feedName:"known_groups"` (plus `subjects:[groupId]` for one group). Posts reach a group through the group's boost (FEP-1b12), so the booster is the group, not a person. Group addresses are `&name@host` (`+name@host` for topics); Fedizen pages are `/group/<name>` and `/+<name>`. Joining and leaving go through the person's Fedizen connection: `/api/v1-bonfire/groups/:id/join|leave`, and Mastodon follow/unfollow for announcement channels; membership is read from `/api/v1/accounts/relationships`. Avatars — people, groups, podcasts and other accounts alike — follow the reader's avatar shape (Settings → Appearance: circle by default, rounded or square; src/lib/avatar-shape.ts sets --atlas-avatar-radius). Draw every avatar with that variable (CSS classes) or the .atlas-avatar class (Tailwind), never a fixed radius; post images and episode artwork keep their own corners.
- Fedizen groups, as measured live (rc.1, Nov 2026): `categories` caps `limit` at 100 (more returns a 500) and pages with `after:[Cursor!]` / `pageInfo{endCursor hasNextPage}`; ~800 categories, about half groups, the rest topics. `boundaries` and `membersCount` are the slow fields, so lookups that don't need them leave them out. An unknown id comes back as the error " Not Found.". Groups without their own images get Bonfire's /images/avatar.png and /images/bonfires.png, which Atlas ignores. `/api/v1/accounts/relationships` reports a joined group as `following: true`.
- Intelligence (desktop /settings/intelligence, phone pushed page /intelligence/) is opt-in AI with the person's own key: Anthropic, OpenAI, Google Gemini, Mistral, Moonshot Kimi, Cloudflare Workers AI. Keys are encrypted server-side (AES-256-GCM, HKDF from the ATLAS_AI_KEY_SECRET Worker secret, AAD bound to user+provider, rotation via ATLAS_AI_KEY_SECRET_PREVIOUS), live in atlas_ai_keys (RLS on, no policies: service role only), are never returned to the browser or logged, and only go to their provider's fixed endpoint (llm.ts). Opt-in "on this device only" keys (device-keys.ts) stay in IndexedDB under a non-extractable AES-GCM key and the browser calls the provider itself (Anthropic with anthropic-dangerous-direct-browser-access; never Cloudflare, whose API refuses browsers); Settings must keep saying a page script could read such a key. AI tasks (tasks.ts) run on the server for server keys and in the browser for device keys; the assistant needs a server key. Server keys: several per company (atlas_ai_keys row per key: id, optional label, its own model; supabase/migrations/20261123000000_ai_key_roles.sql). Roles (intelligence/roles.ts, store.server withAi): main (assistant, alt text, translation, writing/suggesting filters, search wordings) uses settings.main_key, then with `fallback` the other keys in the order added; background (judging posts against filters as feeds load) uses background_key/background_model or the main ones, and its backups never include the main key. Embeddings use one key only (embeddingPick: background chain, then main; never a backup, so the index isn't split). A key a provider rate-limits rests 60 s per server instance: background skips it, main tries it last. Errors that another key won't fix (bad-output) stop the chain. Device-only keys stay one per company with no roles or backups yet. Model ids are never hardcoded as existing: they come from the provider's model list for that key. Never send temperature (recent Claude/OpenAI models reject it). Never use Atlas's own AI credit: /api/chat requires sign-in and the person's key.
- Keyword filters (atlas_content_filters, applied by ContentFilterProvider through FilterGate / MobileFilterGate in feed cards, Local, groups and profiles; FilterPlaceProvider marks home, public or account): Bonfire's syntax (whole words, * wildcards, look-alikes folded) without its lossy parts (no "rn"→"m" folding, reads hashtags, CW, alt text, link preview, poll options, quoted posts). From Bluesky: no-space scripts (Han, kana, Hangul, Thai…) match anywhere, "n-f-t" reads as "nft" but "and/or" never as "andor", own posts never filtered, "not from people I follow" (relationships, 40 at a time), expiry. From Mastodon: places (contexts), hide / warn / blur media, hidden posts show as notices on a profile, Mastodon's JSON import/export. Notices say why (matched words, or judged by the model); AI wordings are editable; "Filter posts like this" sits in each post's More menu. With Intelligence on, word matches are checked in context by the person's model and filters get AI-found wordings; deep matching (opt-in) checks every public post. Direct messages never go to the AI. If the AI fails, filters fall back to words. Bonfire lists /api/v2/filters as "coming soon": switch to it for sync once it ships.
