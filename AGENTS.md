# Architecture
- Initialize account state through the subscribe-first session observer and associate loaded profiles with their user ID; delayed reads must not overwrite newer auth events or display another account's profile.
- Share article creator attribution through CreatorTag across phone and desktop feeds; profile and follow actions use the existing discovery state so author interactions stay consistent.
- Open-web article authors (Spotlight, readers): resolve in src/lib/article-author(.server).ts — the article's ActivityPub attributedTo first, then fediverse:creator via WebFinger, else the plain byline. Credit an actor only if it shares the article's host or lists that domain in attributionDomains; fetch only through safeFetch (public https, every hop resolved over DoH and refused unless all addresses are public, re-validated redirects, timeout, size cap); always re-fetch attributedTo actors from their own server, never trust embedded copies and never block Spotlight past its time budget.
- App dock order is Feeds, Discover, Groups, Activity, then the person's avatar (Profile); the tab bar, side tab bar, rail and sidebar all render the same `dock` list. Settings is reached from Profile and the sidebar, Saved is a tab on Profile.
- Profile is the dock's last tab (ProfileView), structured like a Bluesky profile: banner, avatar, Edit profile, name, handle, counts, bio, then tabs Posts, Replies, Media, Saved (owner-only, private), Feeds, Lists. Follows open from the Following count, never as a tab. Never seed fictional personal content for its empty sections (Groups follows the same rule).
- Saving requires sign-in: SocialProvider's `canSave` gates `toggleSave`; signed-out Save actions offer sign-in instead.
- Keep creator catalogue and filtering in browser-safe modules, separate from presentation, so sample discovery can later be replaced by a live source.
- Share session-only follow/save state through a root provider across discovery routes; do not imply account persistence until connected.
- Keep the existing AI assistant transport unchanged during presentation-only product pivots.
- Keep Compose independent of assistant opt-in; use a draft-only composer until social publishing is connected, to avoid implying posts were published.
- Use a settings layout with separate leaf pages for categories so each setting has a navigable URL.
- Accounts: profiles hold display name and avatar_key; avatar_key maps to bundled memoji assets in src/lib/atlas-avatars.ts, never stored as build-hashed URLs; session state comes from AtlasAuthProvider in src/components/social/AuthState.tsx, the single onAuthStateChange subscription.
- Phone app: Framework7 lives only at /app (src/components/f7), lazy-loaded client-side; the original site stays untouched so either can be dropped independently. /app serves every device (no desktop redirect).
- Device profile (src/lib/device-profile.ts, tested in tests/device-profile.test.ts): layout comes from window size and the fold only (size classes + Viewport Segments / Device Posture), never from device identity; identity only picks the iOS or Material theme and labels the device. Wide windows mirror the desktop Discover page (feed + "Voices to know" column, reusing the desktop components inside .atlas-desktop-embed, which rolls Framework7's unlayered globals back to Tailwind's layered values); folding changes only the panes (feed on one screen, voices on the other); navigation stays put. Keep controls clear of each safe-area edge independently (insets can be asymmetric) and of the crease; read insets from env() because Framework7 zeroes --f7-safe-area-* at the root.
- PWA: manifest plus a /app-scoped service worker (public/sw.js, registered in production only): network-first navigations with an offline /app shell, cache-first hashed assets; API, auth, server-function and non-GET requests are never handled, and use Service Worker static routing to skip the worker where supported.
- Fedizen content: read public Bonfire data via its GraphQL API (feedName "articles" for Recent Articles, "local" for the signed-out public feed; fall back to object.creator when subject is hidden) in src/lib/bonfire.server.ts; render remote HTML only as plain-text paragraphs. Mastodon REST timelines on Fedizen require login.
- Fedizen API access: separate read-only "Connect Fedizen" OAuth (PKCE, per-callback app registered via /api/v1/apps) stored in server-only tables (no anon/authenticated grants); tokens never leave server functions in src/lib/fedizen.server.ts.
- Optional relay: relay/ is a standalone Bun + @fedify/relay package outside the app build (one process per protocol, own origin and PostgreSQL); Atlas is a Fedizen client, so the relay never auto-deploys or auto-subscribes and only an instance admin subscribes. Keep it allowlist-only, relay only public content from currently subscribed servers (authoritative check runs after Fedify signature verification; Follow/Undo/Accept/Reject are a separate control plane), forward signed bodies byte-for-byte, keep /healthz free of configuration details, pin @fedify/* exactly (it hooks an internal method), and keep relay tests offline via its fetch-blocking preload.
- Bonfire relay client: bonfire_relay_client/ is a standalone Elixir extension outside the app build. It keeps a dependency-free pure core so it can be tested offline. All signing, delivery and fetching go through the Federation behaviour; the Bonfire adapter is capability-gated on the hooks in upstream_patches/ and fails closed without them. Relay subscriptions use the instance service actor only, never a user's follow graph. Hashtag and instance rules are local filters on delivered content, kept separate from selective sources like FediBuzz. Every admin call re-checks authorisation on the server, and the feature stays off by default with connections created idle.
- Relay-client host integration uses a source-matched custom Community image and a full digest override selected from the host's exact Co-op Cloud recipe image expression/overlays; variable names differ across revisions, displayed versions/recipe labels are not provenance, and patch fit does not establish full host compatibility.
